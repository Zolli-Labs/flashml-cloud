## 1. Built, tested, and invisible

### 1.1 The resource-allocation router — **wired 2026-08-12**

`POST /v1alpha1/jobs/preview-plans` was fully built and the console called it
zero times, so the pitch — *jobs route to resources by fit, with price and
speed driving the choice* — was provable only with `curl`.

Now on the job page's **Placement** tab: the workload kind, the one-sentence
evidence for that classification, all four venues with verbatim reasons, the
cheapest/fastest plans, and the fleet counts. Placed above the tab's
"no tasks yet" guard, so a PENDING job still shows where it *could* run, and
deliberately outside the 2.5 s poll — the answer is a property of the spec and
cannot change after submission.

The two refusal kinds are rendered as visibly different statements, which is
the point rather than a detail:

| | meaning |
|---|---|
| `suited: false` — *"Can't run this work"* | physically cannot; no price changes it |
| `acquirable: false` — *"No capacity we can reach"* | a real fit; **our** gap, not a verdict on the venue |

Collapsing them would let the UI imply we *chose* not to use a venue we simply
cannot reach. Where a venue is both, hardware wins the headline and the
capacity gap is added as a second line.

**Pre-submit comparison was investigated and deliberately NOT built.** It is
the stronger story — seeing the options before committing — but it is not
cheaply reachable and the cheap version would lie. `compile_to_jobspec` has
exactly one call site (`app.py:4033`, inside `POST /v1alpha1/jobs/from-repo`)
and no dry-run flag. Producing the spec the submit path would produce requires
the whole pipeline including **dataset resolution over the network**;
`compile.py:_dataset_slices` raises `CompileError` when datasets are declared
and nothing resolved, so a repo with a `datasets:` block cannot be compiled
without it. Passing empty manifests changes the task count — and that count
feeds `classify(raw_spec, task_count=…)` straight into the rendered sentence
(*"expands to N independent trials"*). A preview claiming 40 trials for a job
that submits as 4 is exactly the lie the honesty rules forbid. Duplicating the
pipeline would create the second copy this workspace has a documented
production bug about. Left for a task that can do it properly.

### 1.3 Artifacts — **closed on the API side 2026-08-11**

No browser listing route existed; the console read `job.artifacts`, which is
always `[]` for lease-backed jobs, so the Artifacts card was empty for every
job.

**Correction to an earlier draft of this document:** it claimed
`artifact_mirror.py` had "no callers at all". That was wrong, and it came from
a `grep` truncated by `head` — the conclusion was drawn from cut-off output.
Mirroring was already wired in commit `71d5034`: `_mirror_job_artifacts` fires
from `GET /v1alpha1/jobs/{job_id}` when the job is terminal and
`artifacts_mirrored_at` is unset, guarded by the `0016` marker so it runs once
rather than once per two-second poll. Best-effort, nothing stamped on failure.

Now added: `GET /v1alpha1/jobs/{job_id}/artifacts` (browser, viewer-checked,
keys relative to the job prefix so they compose with the fetch route), and a
**307 to a presigned OSS URL** on download when the job is mirrored and OSS is
configured — otherwise the coordinator proxy, byte for byte as before. Every
OSS failure falls back to the proxy rather than erroring, because the
coordinator still holds every byte and a 502 for a reachable file would make
configuring OSS worse than not configuring it.

All of it gated on `Settings.oss_configured`: with OSS unset the product
behaves exactly as before and uploads nothing.

**Correction, 2026-08-11 (later the same day).** This section previously said
"a plain `<a download>` is unaffected". **That was wrong and it shipped a
bug: every download answered 401.** The download route sits on `current_user`,
which reads a bearer token from the `Authorization` header and from nothing
else — and a browser NAVIGATION sends no such header, so the anchor never got
as far as the 307 it was written to follow. Reverting to a `fetch()` was not
the fix either: it trades the 401 for a CORS failure on the OSS hop and pulls
whole model weights through browser memory.

What replaced it: `GET /v1alpha1/jobs/{job_id}/artifact-url/{key:path}`, an
ordinary authenticated JSON call answering `{storage, url}`. The console
fetches it *with* the header (same origin as every other call it makes) and
then navigates to the presigned URL, which needs no header of ours — it is
OSS's own single-object, expiring grant. Anything not mirrored is fetched
through the API with the header, as a Blob, which is bounded by the
coordinator's 5 GB disk. **A per-key fallback is mandatory:** only ACCEPTED
work is mirrored (hard rule 4), so a FAILED shard's `stderr.txt` is
coordinator-only under a job whose listing says `storage: "oss"`, and a
console that trusted the job-level value would break on exactly the file
somebody opens after a failure. `Content-Disposition: attachment` is set on
both paths (named from the flattened key), without which a navigation to a
JSON artifact *renders* it and navigates the console away.

The route is a **sibling segment**, not `.../artifacts/{key:path}/download-url`:
`{key:path}` is greedy and artifact keys are arbitrary, so the suffix form is
ambiguous by construction — a job that wrote a file called `download-url`
would find its own bytes unreachable.

**Still open.** A federated run's listing answers empty on purpose: fanning
out over rounds would return keys under a *different* job's prefix, which do
not compose with the fetch-by-key route, so every link built from them would
404. A per-round shape both routes agree on is its own task.

## 2. Where the pitch outruns the code

None of these are bugs. They are places where the honest sentence is narrower
than the exciting one, and the venue layer's own notes already say so — which
is the right instinct to keep on stage.

| Claim | Reality |
|---|---|
| "Fine-tuning goes to RunPod" | `_RUNPOD.acquisition = MANUAL`. Zero `ResourceProvider` implementations exist. Capacity appears when a **person** starts a pod running `flashnode work` and it enrols itself. |
| "Alibaba is better for inference, so inference runs there" | `_FC_GPU.acquisition = NONE`. Nothing creates an FC GPU function, so no candidate can carry that venue. Today Alibaba means the **CPU sandbox only** (2 vCPU, 2 GB, `gpuConfig: null`). |
| "Inference" | FlashML has **no serving path at all**. `INFERENCE` means batch forward passes, not an endpoint. The evidence string says so. |
| "HPO runs on every device" | True only for CPU trials. A GPU sweep is refused `fc-sandbox` on hardware. |

The recommended framing is to lean into this rather than around it: *what we
route today, what we have measured, what is not wired yet.* A judge can
puncture the broad claim in one question; they cannot puncture the narrow one.

## 3. Not verified against reality

### 3.1 The Alibaba credentials — **OSS verified 2026-08-12, the loop is not**

**OSS is proven.** `scripts/competition/oss_smoke.py` runs put → head → get →
presign → *unauthenticated* fetch → delete through our own `OSSArtifacts`
class against the real bucket with the real RAM key, and passes. The
unauthenticated fetch is the load-bearing one: it is exactly what a browser
does when the download route answers its 307, so the serving design now has
evidence rather than an assumption.

Getting there surfaced two faults that would each have failed silently:

* The bucket was **LRS** while the purchased plan is **ZRS**, so the plan
  would have offset nothing. Replaced by `zolli-flashml-artifacts-zrs`
  (Singapore / Standard / ZRS / private). Region, redundancy **and** storage
  class must all match the plan; any one of them wrong costs the whole
  purchase, and nothing warns you.
* The RAM policy was scoped to the **old bucket name**, so every write would
  have 403'd. Now `flashml-oss-artifacts` **v2**. This is the failure the
  smoke test exists to catch, because mirroring is best-effort and swallows
  its own errors — a job would simply have stayed `storage: "coordinator"`
  for ever with nothing in any log to explain it.

The FC Sandbox credentials were separately exercised earlier (hibernation
measured live, `flashnode` enrolled from inside a sandbox, ~$0.05 spent).

**What is still unverified: the loop.** `run_demo.py` has only ever run
against a fake control plane, so no end-to-end run has gone through the dev
API with real credentials. That remains the highest-risk unknown.

## 5. Upstream (public repo — needs a release and a four-site pin bump)

Not affordable before 2026-08-15. Full detail and rationale in
`2026-08-11-checkpoint-always-on.md` §4. In priority order:

1. Make the `checkpoint_latest` failure non-fatal in flashnode. Today a
   coordinator outage at task start holds a lease to expiry and pushes a
   healthy host toward quarantine. Mitigated cloud-side by a 7 s retry ladder;
   **the residual window is real and this is the only real fix.**
2. Split the relay / resume-staging gate so the cloud has more than one bit.
3. `CHECKPOINT_MANIFEST_COMMITTED` never reaches a job's event feed (scoped
   `"<job>::<task>"`). The console works around it by polling.
4. A non-numeric `step-*.json` re-fails every 0.3 s for a whole task.
5. `CheckpointCatalog._manifests` / `_registered` are unbounded.
6. `flashruntime.torch.checkpoint()` writes a shape the relay cannot ship —
   the runtime's own PyTorch helper produces checkpoints the runtime's own
   relay ignores. The real fix is multi-part relay support.
7. `GET .../checkpoints/latest` is unauthenticated on the coordinator and now
   sits on every job's critical path. Belongs in the existing "artifact READS
   unauthorized" audit ledger.
