# Web App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The surface a real person touches: sign in with Google, approve a machine from your phone, submit a repo, and watch it train — on a laptop or a phone, with nothing else installed.

**Architecture:** Next.js App Router against the cloud API. Supabase Auth handles Google sign-in in the browser and issues the JWT every API call carries. The app holds **no** business logic and talks to **no** database — it renders what the API returns, because the API is the only component permitted to read Postgres.

**Tech Stack:** Next.js 16 (App Router), React 19, Tailwind 4, `@supabase/supabase-js` + `@supabase/ssr`. The existing dark design system and `components/ui` primitives stay — **this is a rewiring, not a redesign.**

This is **Plan 5 of 7** for M1, implementing the browser half of §3.3 and §10 of
`docs/superpowers/specs/2026-07-31-deployed-multi-user-poc-design.md`.

---

## What already exists, and what is stale

`apps/web` was seeded from an earlier prototype. Pages exist (`/dashboard`, `/jobs`, `/nodes`, `/submit`, `/launch`, `/visualize`, `/integration`) and the design system is good — dark tech, Tailwind 4, a `components/ui` set worth keeping.

**`lib/api.ts` is stale and must not be trusted as a reference.** Its own header says it targets a "retained legacy FastAPI coordinator" started from a `legacy/coordinator` directory, and its `TrainRequest` shape (`k`, `n_points`, `node_type`) describes an API that no longer exists. Read it to harvest UI components, never to learn the current contract. The real contract is `apps/api/flashml_cloud_api/app.py`.

## Global Constraints

- **The browser never touches Postgres.** RLS denies `anon` and `authenticated` outright — verified against the live database, both roles see zero rows. Every read goes through the API. Do not add `@supabase/supabase-js` database calls; use it **only** for auth.
- **The anon key is the only Supabase credential the browser may see.** The service-role key and the coordinator's operator token must never appear in client code, `NEXT_PUBLIC_*` vars, or a bundle. A leaked service key bypasses every ownership check the API performs.
- **Every API call carries the Supabase JWT.** A page that renders without one is a bug, not a "logged out state" — the API returns 401 and the UI must handle it as sign-in-required.
- **Phones are first-class.** The acceptance test has a friend approving a machine from a phone browser. Every screen must be usable at 375 px wide; the approve screen especially, since it exists to be used on a phone.
- **Never claim a capability the backend lacks.** No GPU toggles, no "invite a teammate", no billing. The UI must not imply features M1 does not have.
- Baselines: cloud API **75+ passed, 0 skipped**. Do not break the API while wiring the client.

### Task 1: Supabase auth wiring

**Files:** `lib/supabase.ts`, `middleware.ts`, `app/(auth)/sign-in/page.tsx`, `app/auth/callback/route.ts`

Install `@supabase/supabase-js` and `@supabase/ssr`. Browser client from `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY`; server client for route handlers. Middleware refreshes the session and redirects unauthenticated users from private routes to `/sign-in`.

Sign-in page: one Google button, product name, one sentence on what the product does. Nothing else.

**Manual step nobody can infer from the repo — document it in `apps/web/README.md`:** Google OAuth must be enabled in the Supabase dashboard (Authentication → Providers → Google) with a Google Cloud OAuth client, and the callback URL registered. Until that is done, sign-in returns a provider error rather than a redirect. Write down the exact callback URL the app expects.

**Verify:** `npm run build` succeeds; signing in redirects to `/machines`; signing out returns to `/sign-in`; a private route while signed out redirects rather than rendering an empty shell.

---

### Task 2: The typed API client

**Files:** `lib/cloud-api.ts`, `lib/cloud-api.test.ts`

One module, every call, JWT attached from the current session. Functions mirror the API exactly: `getMe`, `listMachines`, `revokeMachine`, `approveDeviceCode`, `listJobs`, `getJob`, `cancelJob`, `submitFromRepo`.

- A 401 throws a typed `NotAuthenticated` the UI turns into a redirect — never a silent empty list, which would look like "you have no machines" when it means "you are signed out".
- A 404 on a job throws `NotFound`. The API deliberately returns 404 rather than 403 for another user's job so existence is not leaked; the client must not "helpfully" turn that into "access denied".
- Never send the service-role key. Never read `process.env` for anything but the two `NEXT_PUBLIC_` values.

Tests (vitest or the repo's existing runner — check what is configured, add one if none): the JWT is attached; a 401 raises `NotAuthenticated`; a 404 raises `NotFound`; the base URL comes from config, not a hardcoded host.

### Task 3: Approve a machine (`/activate`)

**Files:** `app/activate/page.tsx`

The screen a friend opens **on their phone** while `flashnode login` waits on their laptop. Large code input, forgiving of case and spaces (the code alphabet already excludes `O`/`0`/`I`/`1`, so do not fight the user over formatting), a clear success state naming the machine that was approved, and honest errors: expired, already used, not found.

After success, tell them what happens next — the machine will appear in `/machines` and can start taking work — because a code screen that just says "OK" leaves the person unsure whether anything happened.

**Verify at 375 px.** This is the one screen most likely to be used on a phone, and the acceptance test depends on it.

---

### Task 4: Machines

**Files:** `app/machines/page.tsx`, a `MachineCard` component

List the caller's machines: name, platform, online/offline from `last_seen_at`, and when it last contributed. A revoke button with a confirm step, since revoking is disruptive and irreversible from the UI.

Empty state is a real screen, not a blank page: it is what a brand-new user sees first. Show the exact two commands to enrol a machine (`pip install flashnode`, `flashnode login --coordinator <url>`) so the path from "signed up" to "contributing" is visible without documentation.

---

### Task 5: Submit a repo

**Files:** `app/submit/page.tsx`

Paste a GitHub URL, pick a branch, submit. The interesting part is **preflight findings**: when the API refuses, render every finding at once — level, code, and message — not just the first. Errors block; warnings are shown with an explicit "submit anyway".

This screen is where a user learns that their code needs a package the curated image lacks, or that it cannot reach the network. Make those messages prominent and quote the API's text verbatim — it already names the offending package and which image would provide it. Do not paraphrase a diagnostic into something vaguer.

Depends on Plan 4's `POST /v1alpha1/jobs/from-repo`. If Plan 4 has not landed, build against the plain `POST /v1alpha1/jobs` and leave the repo path behind a flag rather than faking preflight.

---

### Task 6: Jobs

**Files:** `app/jobs/page.tsx`, `app/jobs/[jobId]/page.tsx`

List: the caller's jobs, status, created, name. Detail: status, per-round progress for federated averaging (round, participants, mean loss — the numbers the driver already reports), which machines contributed, and links to result artifacts. Cancel, with a confirm.

Poll on an interval; do not build SSE (that is a later milestone, and polling is honest at POC scale). Stop polling on a terminal state so a finished job does not hammer the API forever.

**Do not invent metrics.** Render what the API returns. If a number is not available yet, omit the element rather than showing a plausible-looking zero — a fabricated metric in a training dashboard is worse than a missing one.

---

### Task 7: Delete the stale client, then verify the whole flow

Remove `lib/api.ts` and any prototype page still importing it (`/launch`, `/visualize`, `/dashboard`, `/integration` are candidates — check each). A page that renders against an API that no longer exists is worse than a deleted one: it looks like a feature.

`npm run build` must pass with no unused-import or type errors. Then walk the §10 acceptance path by hand on a phone-sized viewport: sign in → approve a machine → see it listed → submit a job → watch it progress → open the result.

Update `apps/web/README.md` with the env vars, the Google OAuth manual step, and how to run against a local API.

## Self-Review

**Spec coverage.** §3.3 browser flow → Tasks 1, 3, 4, 5, 6. §5.1 JWT on every call → Task 2. §10 acceptance (phone sign-in, approve, submit, watch) → Tasks 3, 5, 6, 7.

**Deliberately not here:** SSE streaming (polling is honest at this scale), host earnings/credits (no backend), GitHub OAuth for private repos (M1 is public-repo only), any billing surface.

**Type consistency.** `lib/cloud-api.ts` is the single source of API types; pages import from it and define no shapes of their own. `NotAuthenticated`/`NotFound` are raised in Task 2 and handled in Tasks 3–6.

**Known risk.** Task 1's Google OAuth needs dashboard configuration that cannot be done from the repo, and sign-in fails confusingly without it. Task 1 must write the exact steps and callback URL into the README, or the first person to clone this loses an hour.
