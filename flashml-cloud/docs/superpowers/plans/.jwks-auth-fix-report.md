# JWKS auth fix — Supabase ES256 tokens

**Status: done.** Sign-in was broken for every user: the live Supabase
project's CURRENT key is `ECC (P-256)` (rotated ~8h before this work), so
every newly-issued access token is `ES256`, while `verify_supabase_jwt`
verified only `HS256` against `SUPABASE_JWT_SECRET`. Every token failed.

## What changed

`flashml_cloud_api/auth.py` now picks a verification path from the token
header and passes `algorithms=` explicitly on both:

- `alg: HS256` → verified against `settings.supabase_jwt_secret`, if one is
  configured. If none is, the token is **rejected outright** — it is never
  quietly re-checked against a JWKS key, which is the RS256→HS256 confusion
  attack (public key used as an HMAC secret). A dedicated test forges exactly
  that and asserts rejection.
- `alg` in `ES256/384/512, RS256/384/512` → `PyJWKClient` resolves the key
  whose `kid` matches, from `{supabase_url}/auth/v1/.well-known/jwks.json`.
  The allowed algorithm is then the one the *JWK itself* declares, and it
  must equal the header's. `HS256` is not in that set, so a `kty: oct` JWKS
  entry can never be reached.
- anything else, including `alg: none` → rejected before any key lookup or
  network call (asserted: `stub.fetches == 0`).

Every failure inside the JWKS path — unknown `kid`, no `kid`, malformed JWKS,
Supabase unreachable — is caught and re-raised as `AuthError`. It fails
**closed**: never an uncaught exception (that would be an unauthenticated
remote 500 and a 500-vs-401 oracle) and never an accepted token.

`options={"require": ["exp", "sub", "aud"]}` and `audience="authenticated"`
survive on both paths, and are re-asserted on the ES256 path too (PyJWT only
validates those claims when present, so omitting `exp` would otherwise mean
a token that never expires).

**Caching.** One `PyJWKClient` per JWKS URL for the life of the process, in
a module-level dict behind a `threading.Lock` (FastAPI runs the sync
`current_user` dependency on a threadpool). `cache_jwk_set=True`,
`lifespan=300`, `timeout=10`. A per-request fetch would put a network round
trip in front of every authenticated call and hand any anonymous caller a
way to hammer Supabase through us. Tested: 5 verifications → 1 fetch, and
`_jwks_client(s) is _jwks_client(s)`. `reset_jwks_cache()` exists for tests
and for an operator who rotated and does not want to wait out the lifespan.

**Settings.** `SUPABASE_JWT_SECRET` dropped out of the `require_auth`
missing-secret check and now defaults to `""`. `SUPABASE_URL` is the
mandatory Supabase input instead — the JWKS is derived from it — and a
missing one is still a hard `RuntimeError` at startup.

**Packaging.** `pyjwt>=2.8` → `pyjwt[crypto]>=2.8`. PyJWT cannot verify
ES256 without `cryptography`.

## Verification

- `362 passed, 0 skipped` (baseline was `339 passed, 0 skipped`; +23, no
  skips, nothing weakened).
- No unit test makes a network call: `PyJWKClient.fetch_data` is the only
  outbound path and every JWKS test replaces it. The real `PyJWKClient` still
  does `kid` matching and JWK→key conversion, so that logic is exercised for
  real rather than stubbed away.
- Separately, a one-off live check confirmed the deployed fix resolves the
  real key: `kid 4e9dc52b-764e-49c4-9b10-5c2af9a94312`, `ES256`, `EC`.

## One thing found along the way

`create_app()` branches on `SUPABASE_URL` being present to choose the cloud
app vs. the legacy local app, so a deploy missing *only* the URL does not
raise there — it falls back to the legacy app. That is pre-existing and
intentional, but it means the "missing URL fails loudly" guarantee lives at
`Settings.from_env()`. Both are now pinned: `create_app` must not serve
`/v1alpha1/me` without a URL, and `Settings.from_env()` must raise.

## Docs

- `render.yaml`: `SUPABASE_JWT_SECRET` **kept** as an optional `sync: false`
  entry rather than dropped. Dropping it would strand any not-yet-expired
  token signed by the PREVIOUS HS256 key, and would leave no declared slot
  for a self-hosted/older HS256-only project. It now carries a comment saying
  it is legacy, that this project's CURRENT key is ECC (P-256) so it should
  be left blank, and that `SUPABASE_URL` is the required one.
- `flashml-cloud/apps/api/README.md`: new (there was none). Full env-var
  table marking the secret optional and the URL required, plus the ES256/JWKS
  explanation, the caching and fail-closed properties, and when you would
  still set a secret.
- `flashml-cloud/apps/web/README.md`: its pointer at "apps/api's own docs for
  `SUPABASE_URL` / `SUPABASE_JWT_SECRET`" now points at the new README and
  says there is no shared secret to set.
