# Pools v1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Per-device opt-in pool bindings, machine trust badges, a standing capped group invite link, and an in-product Colab/RunPod connect panel with auto-attach.

**Architecture:** One new binding table narrows the existing server-side membership stamp (`bindings ∩ owner's live memberships`); everything downstream — coordinator, protocol, flashnode, the seventh gate, heartbeat revocation — is untouched because placement only ever sees the stamped list. Badges are display-only columns persisted best-effort on the register proxy. Spec: `../specs/2026-08-03-pools-v1-1-design.md`.

**Tech Stack:** Python 3.12 (FastAPI, psycopg 3), Next.js 16 App Router + vitest. All work in flashml-cloud on `develop`; no runtime releases, no render.yaml change, no e2e additions (the coordinator's view is unchanged — spec §7 states this so nobody adds a redundant one).

## Global Constraints

- **Opt-in**: a machine with no binding serves NO pool. The stamp is `machine_pools ∩ pool_members(owner)` — membership stays the authority; a binding without live owner membership grants nothing. Fail-closed-to-`[]` on lookup failure, overwrite-never-merge, str-cast sorted ids: all unchanged from v1.
- **Badges are display-only by construction**: the four capability booleans on `machines` are never read by placement or any authorization path.
- Migration law: `create table if not exists`, `comment on table`, `enable row level security`, zero `create policy`, index FK lookups, 0004-style header + the two boilerplate paragraphs; never edit an applied migration. `tests/test_schema.py` `ALL_TABLES` gains `machine_pools`.
- 404 doctrine everywhere new: unknown and not-yours are indistinguishable; malformed uuids get the established `InvalidTextRepresentation` → not-found guard (four sibling sites exist).
- Invite tokens: raw shown exactly once; only hashes stored; the state endpoint returns NO token material.
- Copy rules (spec §5/§6): invite defaults `uses=10` (cap 100, bool rejected), `expires_hours` default 720 (30 days, cap 2160); the Colab tab leads with the paid-tier ToS box verbatim from `docs/guides/join-a-pool-colab.md`.
- Suites at start: api 588 passed / web 102 passed (from `pytest -q` in `flashml-cloud/apps/api` with `.venv/bin/pytest`; `npm test` in `flashml-cloud/apps/web`). No regressions, ever.
- Behavior change to state in PROGRESS and the migration header: on deploy, existing pools go quiet until machines are ticked in (intended, owner-approved).

```python
def pool_ids_for_machine(db: psycopg.Connection, machine_id: str) -> list[str]:
    """Pools this MACHINE serves: its explicit bindings, intersected with
    its owner's live memberships.

    The join through ``machines`` to ``pool_members`` is the authority
    check: a binding to a pool the owner has left (or was removed from)
    must be inert — otherwise removing a member would leave their machines
    still claiming the pool's unsandboxed work through stale bindings.
    Opt-in is the default by construction: no binding row, no pools.
    """
    with db.cursor() as cur:
        cur.execute(
            """
            select mp.pool_id
              from public.machine_pools mp
              join public.machines m  on m.id = mp.machine_id
              join public.pool_members pm
                on pm.pool_id = mp.pool_id and pm.user_id = m.owner_id
             where mp.machine_id = %s
            """,
            (machine_id,),
        )
        return sorted(str(row["pool_id"]) for row in cur.fetchall())
```

The rest follow the section's established idioms (`on conflict do nothing` for bind; single UPDATE for capabilities; `order by created_at desc limit 1` with the validity predicate for `fetch_outstanding_invite`; `delete ... returning token_hash` + `len(fetchall())` for revoke — count only, hashes discarded).
