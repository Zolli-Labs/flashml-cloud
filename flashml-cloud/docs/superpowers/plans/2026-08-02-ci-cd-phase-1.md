# CI/CD Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Stop untested code deploying itself to production, and make the schema of any database answerable instead of remembered.

**Spec:** `docs/superpowers/specs/2026-08-02-ci-cd-and-environments-design.md`

**Architecture:** `autoDeploy: false` in `render.yaml`; GitHub Actions runs four
test jobs and then triggers the Render deploy through the API. Migrations move
from hand-applied SQL to a runner backed by `public.schema_migrations`, with
prod application behind a GitHub Environment approval.

### Task 1: The migration runner

**Files:**
- Create: `flashml-cloud/apps/api/flashml_cloud_api/migrate.py`
- Create: `flashml-cloud/apps/api/tests/test_migrate.py`

**Interfaces produced** (Task 2 and the CI workflow both depend on these):
- `MIGRATIONS_DIR: Path` — `apps/api/migrations`
- `discover(dir: Path) -> list[Migration]` — sorted; `Migration` has
  `.version` (stem, e.g. `0004_attempts`), `.path`, `.sql`, `.checksum`
- `applied(conn) -> dict[str, str]` — version → checksum, `{}` if the table
  does not exist yet
- `pending(conn, dir) -> list[Migration]`
- `apply(conn, dir, *, baseline: bool = False, baseline_through: str | None = None)
  -> list[str]` — returns the versions it applied (or baselined); raises
  `DriftError` on checksum mismatch, `ValueError` on baseline misuse
- `DriftError(Exception)`
- `main(argv) -> int` — CLI: `--database-url`, `--dry-run`, `--baseline`,
  `--baseline-through VERSION`

Rules the tests must pin:
- each migration applies in **its own transaction**
- an already-applied migration whose file changed raises `DriftError` and
  applies **nothing**, not even unrelated pending migrations
- `--dry-run` exits **1** when anything is pending, **0** when clean
- `--baseline` records versions without executing their SQL
- re-running against an up-to-date database is a no-op

- [ ] **Step 1: Write the failing tests**

Create `tests/test_migrate.py`. Use the `postgres_dsn` fixture from
`conftest.py` — but note it applies migrations already, so tests here must
work against a **separate database** on the same server. Create one per test
with `create database`, connect to it, and drop it after; a helper is fine.

Cover, one test each: table created on first apply; all four real migrations
apply from empty; second run is a no-op; a tampered checksum raises
`DriftError` and leaves the database unchanged; `--baseline` records without
executing (assert the table it would have created does **not** exist);
`--dry-run` return codes both ways.

- [ ] **Step 2: Run and watch fail**

```bash
cd flashml-cloud/apps/api && .venv/bin/python -m pytest tests/test_migrate.py -q
```
Expected: collection error / `ModuleNotFoundError: flashml_cloud_api.migrate`.

- [ ] **Step 3: Implement `migrate.py`**

Write it to the interface above. Points that are easy to get wrong:

- Use `psycopg.connect(dsn, autocommit=True)` and manage each migration's
  transaction explicitly with `with conn.transaction():`, so one failing
  migration does not roll back the ones before it.
- `create table if not exists public.schema_migrations (version text primary
  key, checksum text not null, applied_at timestamptz not null default now())`
  — create it before reading, so `applied()` is simple.
- Checksum is `hashlib.sha256(path.read_bytes()).hexdigest()`. Bytes, not
  text: a line-ending change is drift and should be caught.
- **Check every applied migration for drift before applying any pending one.**
  Drift is a property of the whole set, not of the next file.
- The CLI reads `--database-url` or falls back to `$DATABASE_URL`, and prints
  what it did. It must never print the URL (it contains the password).

- [ ] **Step 4: Run and watch pass**

```bash
cd flashml-cloud/apps/api && .venv/bin/python -m pytest tests/test_migrate.py -q
```

- [ ] **Step 5: Commit**

```bash
git add flashml-cloud/apps/api/flashml_cloud_api/migrate.py \
        flashml-cloud/apps/api/tests/test_migrate.py
git commit -m "feat(api): migration runner with schema_migrations and a drift guard"
```

### Task 3: The CI workflow

**Files:**
- Create: `.github/workflows/ci.yml` (repository root — GitHub reads workflows
  from the root only; a copy under `flashml-cloud/` would be inert, which is
  the exact mistake the public repo already made once)

Four jobs on `push` and `pull_request`, plus a fifth deploy job (Task 4).

- [ ] **Step 1: Write the workflow**

`api` job:
- `ubuntu-latest`, Python 3.11 (matches `PYTHON_VERSION` in `render.yaml`)
- **Put the PostgreSQL binaries on `PATH` by discovery, not by hardcoding a
  version**: `echo "$(ls -d /usr/lib/postgresql/*/bin | tail -1)" >> $GITHUB_PATH`.
  `tests/conftest.py` starts its own server and needs `initdb`, `pg_ctl`,
  `pg_isready`, `psql`. A `services: postgres:` container would **not** work.
- install with `uv` (as the `Makefile` does), then `pytest -q`

`web` job:
- Node 20, `npm ci` in `apps/web`, `npm run build`, `npm test`
- `NEXT_PUBLIC_CLOUD_API: https://flashml-api.onrender.com` in `env` —
  `next.config.ts` fails a production build without it, on purpose. Not a
  secret; it is already a literal in `render.yaml`.

`e2e` job:
- `make e2e-setup && make e2e`
- Cache `~/.cache/uv` keyed on `hashFiles('Makefile')` — the pins live there.
  This job downloads torch; without a cache it is the long pole.

`secrets` job:
- `gitleaks/gitleaks-action@v2` with `fetch-depth: 0`.
- If it flags historical commits, **report rather than "fix"**: a live
  `DATABASE_URL` password was pasted into a chat twice on this project, and
  whether those reached git history is a real question that deserves an answer,
  not a suppression rule.

- [ ] **Step 2: Validate the YAML parses**

```bash
python3 -c "import yaml,sys; yaml.safe_load(open('.github/workflows/ci.yml')); print('ok')"
```

- [ ] **Step 3: Commit**

- [ ] **Step 2: Add the deploy jobs**

```yaml

    needs: [api, web, e2e, secrets]

    needs: [migrate-prod]

    ...
```

## Human gates (none of these can be done from this session)

🔒 Repository secrets: `RENDER_API_KEY`, `PROD_DATABASE_URL`.
🔒 GitHub Environment `production` with yourself as a required reviewer.
   **Without this the "gate" is not a gate** — the job would run unattended.
🔒 One-time baseline against `flashml-poc`. **Three commands, in this order.**
   A bare `--baseline` here would be a silent data bug: prod has 0001-0003 but
   NOT `0004_attempts`, and baselining that would record the attempts table as
   created without creating it.

   ```bash
   # 1. record only what is genuinely already there
   python -m flashml_cloud_api.migrate --database-url "$PROD" \
          --baseline --baseline-through 0003_contributions_unique
   # 2. VERIFY: 0004 must still be pending (this exits 1, which is correct)
   python -m flashml_cloud_api.migrate --database-url "$PROD" --dry-run
   # 3. apply 0004 for real -- this is what creates public.attempts
   python -m flashml_cloud_api.migrate --database-url "$PROD"
   ```

   Step 2 is not optional. If it prints "up to date" you baselined too far and
   `public.attempts` does not exist.
