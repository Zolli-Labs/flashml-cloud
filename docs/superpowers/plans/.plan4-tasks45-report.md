## Task 4 — `flashml_cloud_api/preflight.py`

`preflight(config, repo_root, image) -> list[Finding]`, `Finding(level, code,
message)`. All six codes implemented: `entrypoint-missing`, `unknown-import`,
`network-use`, `no-metrics-json`, `writes-outside-out`, `unparseable`.

`network-use` is an **error**. Volunteer nodes run `--network none`; the code
cannot work, so this is not a style preference. Guarding an import does not
downgrade it — the guard proves the code anticipates the *package* being
absent, not the *network* being absent.

Every check is a static `ast` walk. The module contains no `import` of user
code, no `importlib`, no `exec`, no `compile(..., "exec")`, and never touches
`sys.path`. `ast.parse` is fed **bytes** so a PEP 263 coding cookie is honoured
rather than guessed at.

**False-positive suppression** (a check that always fires is as useless as one
that never does — and worse, it blocks legitimate submissions):

- relative imports (`from . import utils`, `from ..pkg import x`) are never
  reported as unknown packages
- `import os.path` / `from os.path import join` resolve against `os`
- a repo-local module imported absolutely (`import utils` next to `train.py`,
  or `mypkg/__init__.py`) is not "unknown" — otherwise the most common repo
  layout would fail on every submission
- imports under `if TYPE_CHECKING:` are ignored (they never run)
- a guarded `try: import torch / except ImportError:` is a **warning**
- a computed (non-literal) path is never judged for `writes-outside-out`
- a docstring mentioning `curl` does not fire; only the *program* of a
  recognised `subprocess`/`os` call does

An import inside a function body or a class body is still detected.

**Scope decision:** the entrypoint file only, not a repo-wide scan. A repo-wide
scan would refuse a submission because the repo's own `tests/` directory
imports `requests`. Preflight is a helpfulness control; `--network none` and
the sandbox are the security controls. Documented in the module docstring.

## Task 5 — `compile.py` + `POST /v1alpha1/jobs/from-repo`

`compile_to_jobspec` emits `workload.type: "command"` with `command` as an argv
list, `inputs` as `artifact://` URIs, and a sweep expanded to one task per
combination through `task_params`. `isolation` is fixed at
`{"tier": "sandboxed", "allowFallback": false}` and is not configurable —
`CommandRecipe` refuses anything else, `flashml.yaml` has no `isolation` key,
and the parser refuses unknown keys, so there is no path from a repo to a
weaker tier. A test runs the compiled spec through the **real**
`CommandRecipe.expand`, not a shape assertion.

Endpoint order is load-bearing: JWT → fetch → extract → parse → preflight →
refuse on any error (all findings at once) → stage tarball → compile → submit →
write the `jobs` row from the verified JWT `sub`.

## Attacking my own work

**Can repo content execute during preflight?** No. Nothing is imported or
run. A test plants `sitecustomize.py`, an `evil.pth`, and an `__init__.py`
that would each write a marker file if anything put the repo on `sys.path`;
another plants an entrypoint that writes a marker at module level. No marker
appears. The `.pth`/`sitecustomize` vector needs a `site` import or a
`sys.path` mutation, and this module has neither.

**Can a crafted entrypoint make us read outside the repo?** No.
`../secret.py`, `/etc/passwd`, and an in-repo **symlink** pointing outside all
resolve-then-contain-check and come back as `entrypoint-missing`, with the
outside file's content absent from the message. `extract_safely` additionally
never materialises symlinks on disk, so the symlink case cannot arise through
the endpoint at all — it is tested against `preflight` directly.

**Can a finding reflect unsanitised repo content?** Not any more — it could
have. Findings quote string literals from user source, parser messages, and
the entrypoint path; `RepoError` quotes an attacker-chosen tar member name;
`ConfigError` embeds a YAML snippet including newlines. All of it now goes
through `safe_text`, which maps control characters (CR/LF above all) to `?`
and truncates. Tests assert no `\n`/`\r` survives into a finding message or a
400 `detail`, and that a 50 KB literal path is truncated. This matters because
the API logs one JSON object per line.

**Can a huge or deeply-nested file hang or blow the stack?** No. A 5000-deep
parenthesis nest returns an `unparseable` finding (CPython's parser guard fires
first); the walk is `ast.walk`, which is iterative, so nothing recurses on user
input. `RecursionError`/`MemoryError`/`ValueError` (null byte) are all caught
and become findings. An entrypoint over 4 MB is refused unparsed rather than
read into the process, and the finding list is capped at 50.

**Does an error finding ever still result in a submitted job?** No, and it is
asserted from both sides: `transport.requests == []` (no artifact staged, no
job submitted) *and* zero rows in the real `jobs` table. Checked for a network/
unknown-import repo, a missing entrypoint, and an unparseable entrypoint. The
refusal happens before the first coordinator call, not after it.

**Other holes found and closed while writing this:**

- `CommandRecipe` runs `str.format` over **every** argv token of a sweep, not
  just the ones with placeholders — so a legitimate `--filter={"a":1}` would
  raise `KeyError` inside the recipe and surface to the user as an unexplainable
  platform failure. Literal tokens are now brace-escaped when a sweep is
  present. Test pins the round trip.
- A sweep key that is not a Python identifier (`learning-rate`) makes
  `"{learning-rate}".format(**params)` raise upstream → a 500 for what is a
  user error. Now refused at compile with a message naming the key.
- A boolean sweep value would have become `1`/`0` on the command line (in
  Python `bool` is an `int`). Now renders `true`/`false`.
- An image reference with a registry port (`registry:5000/img:1.2.3`) split
  wrong on a naive `rpartition(":")`. Now splits only when the colon follows
  the last slash.
- `repo`/`ref` are interpolated into a URL **this server** fetches, so both are
  regex-validated before any fetch: CRLF, `..`, `?`, `#`, a non-github host, and
  a leading `-` are all refused with zero network calls.
- Compile now runs **before** the artifact upload, so a config that cannot
  compile leaves no multi-megabyte orphan in the artifact store.
- The staged code key is `uploads/<uuid4>/code.tar.gz` — not derived from the
  user id or the repo name, so it cannot be predicted and overwritten by
  another user between compile and claim.

## Residuals (not fixed here, both need a decision outside this plan)

1. **`/work/inputs/code/<entrypoint>` does not exist yet on the node side.**
   The plan pins this argv, and it is what Task 5 emits. But
   `flashnode/executor/loop.py` stages an input at
   `workdir/inputs/<basename-of-key>` and does **not** unpack archives, so the
   tarball lands at `/work/inputs/code.tar.gz` and the compiled command would
   fail with "no such file". Closing this needs a flashnode change (unpack the
   `code` input into a directory) or a compile change once that contract is
   settled. Cross-repo, versioned — deliberately not done unilaterally here.
2. **Orphaned staged artifact when the coordinator refuses the submission.**
   If `POST /v1alpha1/jobs` returns ≥300 after the tarball is staged, the blob
   stays. No job row is written (asserted), so nothing is inconsistent — but
   the artifact store needs a GC pass for unreferenced `uploads/` keys.
